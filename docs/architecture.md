# Architecture and invariants

The React interface never receives a SQL connection or filesystem/shell capability. The single Tauri `command` endpoint dispatches an allowlist of actions. Native calls run on blocking worker tasks behind one service mutex, serializing writes away from the UI thread. The single-instance plugin and exclusive store lock prevent concurrent store access. Authentication is held by the backend and cleared on exit, store switching or restoration.

All amount and quantity fields crossing IPC are **decimal strings containing scaled integers**: `"12345"` is AFN 123.45 and `"1250"` is 1.250 base units. UI entry rejects excess precision. Rust checks ranges and uses i128 intermediates with half-up monetary rounding. A cumulative proportional allocation distributes sale discounts exactly without assigning a discount greater than a line's subtotal. Taxes are optional, disabled by default, and configured as basis points per product. No legal tax defaults are embedded.

Checkout writes a sale, immutable line snapshots, lot allocations, stock deductions, inventory movements, payments, customer debt, cash effect, idempotency result and audit record inside one `BEGIN IMMEDIATE` transaction. Foreign keys, uniqueness constraints, WAL and `synchronous=FULL` are enabled. A persistent request UUID returns the previous result on retry; reusing an ID for changed input is rejected. Stored request inputs are SHA-256 fingerprints, never plaintext account passwords. Pending financial request IDs survive frontend restarts. Checkout additionally preserves its pending payload and recovers a committed receipt by ID after an uncertain response.

Product prices and costs, English/Dari names, base units, discounts and tax amounts are snapshotted on sale lines. Carton identifiers translate to an exact quantity of the product's base unit; the saved sale always expresses that base quantity. Lots are allocated by dated expiry first, then receipt time/row order; undated lots use receipt order. Expired lots stay visible in inventory but cannot be sold. Available stock excludes expired lots. Valuation includes all physically held stock, including expired items until a count/write-off removes them.

Returns use cumulative prorating, so repeated fractional refunds exactly reconcile to the original line total. Returns first reduce that sale's outstanding debt and then produce a cash or recorded non-cash refund. Restockable goods restore original lot allocation; expired/damaged goods are not restocked and their cost remains an expense of the original sale. Collections reduce customer debt and never create sales revenue. Supplier return credits may make a supplier balance negative if the supplier has already been paid; this is a credit balance, not automatic cash received.

Cash movements require an open register and cannot reduce expected cash below zero. Closing records expected, counted and variance and prevents subsequent movements on that session. The application models one shared physical register for one store. Completed sales, returns, cash movements and expenses have no delete/edit endpoint.

SQLite migrations are embedded in the executable and tracked using `user_version` and `schema_migrations`. Existing stores receive a SQLite backup before migration. Restore accepts the current schema only, checks integrity and foreign keys and requires an active owner, then preserves the live database and restores through SQLite's online backup API. A failed source validation never replaces the live store.

Reports derive from database transactions and use Asia/Kabul dates. Transaction report ranges are limited to 366 days per request. Inventory and account balance reports represent current balances, not historical as-of balances. Dashboard chart values convert bounded amounts to numbers only for visualization; authorization and posting never use those values. The current snapshot loads permitted store data into memory for sortable client-side tables; very large catalogs/history need server-side pagination and load/performance testing before deployment.

Images are validated PNG/JPEG/WebP blobs (maximum 2 MB each) stored in SQLite, so backup includes branding and product images. Passwords use Argon2id and never appear in snapshots or audit output. Permissions are checked in Rust; hidden sidebar entries are presentation only. Local SQLite files are not encrypted; secure the operating-system account and backup media.

The browser demo service is development-only, loopback-only and refuses real-store mode. Installed desktop assets, fonts, icons and translations are bundled locally. The production CSP permits local assets and Tauri IPC, with no remote application API.

References: [SQLite durability](https://www.sqlite.org/pragma.html#pragma_synchronous), [rusqlite backup API](https://docs.rs/rusqlite/latest/rusqlite/backup/index.html).
